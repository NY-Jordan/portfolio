Clean Architecture gets cited a lot and demonstrated rarely. Most explanations stop at the concentric-circles diagram. Here's what it actually looks like in a shipped product.

## The core idea

Separate your business rules from the frameworks and tools that deliver them. Concretely: your domain logic shouldn't know that Next.js, Firebase, or MySQL exist.

```ts
// domain/booking.ts — no framework imports, just rules
export function canBook(slot: Slot, existing: Booking[]): boolean {
  return !existing.some((booking) => overlaps(booking, slot));
}
```

The framework-facing code calls into this, never the other way around.

## Where it pays off

On Zyraa, the booking engine had to work identically across the admin dashboard, the public booking marketplace, and the POS flow. Because `canBook` didn't know about React or Firebase, all three surfaces could call the same rule without duplicating it — or drifting apart.

## Where it's overkill

For a single-page marketing site or a script you'll run once, this is wasted ceremony. The rule of thumb I use: if the same business rule needs to be correct in more than one place, the separation is worth it. If it doesn't, a plain function in your route handler is fine.

## The trade-off nobody mentions

Clean Architecture adds indentation before it adds value. On a two-week prototype, you'll spend real time wiring interfaces you might delete. It's a bet that the product outlives the prototype phase — make that bet on purpose, not by default.
